# Section: session registry, load path, and the system prompt

## How a tool becomes an activity

`orchestrator/load_tool.py` already does this. Do not add an activity file for a community tool.

- `load_tool_activity` (line 150) loads the tool and returns its spec.
- `register_community_tool` (line 265) registers that spec.
- The registered function calls `workflow.execute_activity(name, tool_context.tool_use, **_ACTIVITY_OPTIONS)` (line 279).
- `@activity.defn(dynamic=True) run_loaded_tool` (line 511) runs the loaded tool's `stream()` through `_run_loaded_tool` (line 243).

`journal`, `environment`, `http_request`, `swarm`, forge, dicom, and fhir use that path. `graph_activity` and the desktop activities already exist. Leave them. The sample `environment_activity` in `.agents/skills/strands-temporal/scripts/strands_plugin/tools/workflow.py` is not a file to copy.

Its `tools` list is the table in "What is registered when a session starts". `journal`, `environment`, and `http_request` get there by calling the existing `load_tool_activity` and `register_community_tool`. `run_loaded_tool` executes them. Do not create `journal_activity.py`, `environment_activity.py`, `http_request_activity.py`, or any other activity file. Do not copy a tool's agent loop. `load_tool` of `graph` dispatches the existing `graph_activity`. `load_tool` of `browser` and the computer-use names dispatches with `task_queue=DESKTOP_BROWSER_TASK_QUEUE` and does not enter `run_loaded_tool`. **Prompting.** "What the system prompt tells the agent" is the text you put in `agent.json`. Keep the three groups separate. A name belongs in one group. Write the ten chains as sequences, and tell the model to stop when an earlier step already answered the question. Do not copy the delegation SOP into `agent.json`. That file does not exist yet and another section writes it. Do not add the tool-selector sentence. Batch 3 adds that one sentence.

**Scope.** In: `orchestrator/workflow.py` (the `tools=` list and the `register_community_tool` calls for `journal`, `environment`, and `http_request`), `orchestrator/load_tool.py`, `orchestrator/agent.json`. ## Outcome

A new session's agent can call only `load_tool`, `discover_tools`, `unload_tools`, `use_skill`, `environment`, `http_request`, `journal`, and the MCP clients the factory returns. `think`, `graph`, `use_agent`, `python_repl`, `browser`, `mcp_client`, `swarm`, and the computer-use actions are not on that list. They are discoverable. `_SESSION_TOOLS` no longer refuses `graph`, `use_agent`, `think`, `browser`, `mcp_client`, or `python_repl`. It still refuses a load that would replace `load_tool`, `discover_tools`, `unload_tools`, `use_skill`, `environment`, `http_request`, or `journal`.

The prompt the model reads names the registered tools, the server-side Agent API tools (`web_search`, `fetch_url`, `image_search`, `people_search`, `finance_search`, `sandbox`, `mcp`, and the GitHub connector), the discoverable tools this plan depends on, each MCP server and what it is for, and the ten chains. `pubmed` and `fda` are stated as absent. Server-side names are not registry names and are not passed in a node's `tools` list.

`load_tool("graph")` runs `graph_activity`. Desktop names run on the desktop queue. `swarm`, forge, dicom, and fhir run through the dynamic activity that already exists.

Add a test that the workflow tool list equals that registry. Run it from `orchestrator/` with `.venv/bin/python -m pytest` on the test file you add. `pytest tests` may still fail collection on `TurnInput` and `_ToolResultHook`. Report that. Do not reintroduce those symbols.
